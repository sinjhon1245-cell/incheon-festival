# 부스 Live 부하 모델 결과

모델 계산값입니다(측정값 아님). Supabase 처리 한도 가정 **400 RPS**, 부스 80곳, 관람객 1명이 600초마다 페이지를 새로 엶, 화면은 모두 켜져 있음(가장 나쁜 경우), 운영자 200명 + 관리자 20명이 함께 씀(7.7 RPS). 같은 인자로 돌리면 같은 표가 나옵니다.

응답 크기(gzip + 머리 400B): settings 679B · zones 551B · booths 1,790B · booth_live 1,073B · (B) master 2,176B · live 스냅샷 1,095B

### B 구조 (100,000명)

- 붕괴 여부: 관람객 origin 요청이 최선 0.43 RPS(관람객 수와 무관), 최악 157 RPS(관람객 수에 비례하지만 Supabase 한도 400 RPS 아래) → 이 가정에서는 Supabase 가 무너지지 않음. 어느 쪽인지는 스테이징에서 x-vercel-cache 로 잼.
- CDN 의 origin 보호: cache hit 최선 99.99%, 최악 97.2%.
- Supabase 장애 10분: stale-if-error(86400s) 동안 엣지가 마지막 정상본을 계속 줌 → 관람객 오류 0, 화면은 스냅샷의 generated_at 으로 '몇 분 전 기준' 을 표시.
- 엣지까지 실패할 때: 클라이언트 지수 백오프(20→40→80→120초, 전체 흩뜨림)로 browser→CDN 요청이 최대 83.3% 줄고, localStorage 의 last-good snapshot 으로 계속 그림.
- 자동 회복: origin 부하가 관람객 수에 비례하지 않으므로 쌓인 재시도가 없음 → Supabase 가 돌아온 다음 갱신(≤5s)에 회복.
