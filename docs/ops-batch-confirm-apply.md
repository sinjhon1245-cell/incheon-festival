# ‘확인 필요’ 일괄 확인 — Production 적용 · 현장 검증 절차

`supabase/migration-booth-live-check.sql` 을 Production 에 적용하는 절차입니다. **실행 직전에 최종 승인을 받고, SQL Editor 에서 운영 담당자가 직접 실행합니다.**
설계는 [ops-batch-confirm-and-notify.md](ops-batch-confirm-and-notify.md) 2장, 읽기 전용 점검 SQL 은 `supabase/check-booth-live-check.sql`(A~F 묶음).

## 0. 한 장 요약 — 운영 담당자용

모두 Supabase **SQL Editor** 에서 합니다. 파일은 `supabase/` 폴더의 세 개입니다: 점검 `check-booth-live-check.sql`(읽기만) · 적용 `migration-booth-live-check.sql` · 되돌리기 `rollback-booth-live-check.sql`.
점검 파일은 A~F 묶음으로 나뉘어 있으니 **그 묶음만 골라** Run 합니다.

**언제**: 낮 10:00~17:00. 22:30~23:30(23:00 자동 초기화)과 행사 시간(11-06 · 07)은 피합니다.

**적용(5분)**

1. 점검 **A** Run → ‘선행 조건 있음’ · ‘새 이름 아직 없음’ 두 칸 모두 `true`. 아니면 멈춤.
2. 점검 **E** Run → 결과를 캡처(‘전’).
3. **최종 승인을 받은 뒤** 적용 파일 전체를 붙여넣고 Run → 오류 없음 · 맨 아래 10줄의 ‘맞음’ 이 모두 `true`.
4. 점검 **E** 다시 Run → ‘전’ 캡처와 칸마다 같음.
5. 관리자 화면 [새로 고침] → 부스 운영 현황의 [일괄 확인] 이 ‘준비 중’ 이 아니고 누를 수 있음.

**확인(적용 뒤 처음 쓰는 날)** — 5장 표를 그대로 따릅니다. 요점만:

- 일괄 확인은 **기록만 남깁니다**. 운영자 대기시간 · 마지막 입력 시각 · 관람객 화면은 바뀌지 않아야 합니다.
- 확인한 부스는 ‘확인 필요’(30분 넘음) 표시가 **그대로 있고** 옆에 ‘관리자 확인 HH:MM’ 이 따로 붙습니다. 운영자가 새로 입력하면 그 표시가 사라집니다.
- 관리 조치의 수: 확인 필요 = 관리자 확인 + 아직 미확인.

**되돌리기(1분) — 아래 중 하나라도 보이면 바로**

- 적용 3번에서 오류 · 4번에서 ‘전’ 과 다름(그 사이 운영자 입력으로 바뀐 booth_live 두 칸은 제외)
- 운영자 입력이 실패한다는 신고 · 관람객 화면이 확인 뒤 달라짐 · 5장 기준과 다른 숫자

1. 되돌리기 파일 전체를 붙여넣고 Run → 맨 아래 4줄의 ‘맞음’ 이 모두 `true`.
2. 관리자 화면 [새로 고침] → [일괄 확인] 이 다시 ‘준비 중’, ‘관리자 확인’ 표시 없음(‘확인 필요’ 는 원래대로).
3. 점검 **E** Run → ‘전’ 캡처와 같음.

되돌려도 운영 데이터는 그대로입니다(일괄 확인은 처음부터 booth_live 를 쓰지 않음). 기록 표 `booth_live_check` 는 지우지 말고 둡니다(감사 기록 · 아무도 읽거나 쓰지 못함).
**하지 않는 것**: 리허설 관리의 ‘채우기’(84곳 모두 씀), 부스 · QR · PIN 변경, 기록 표 삭제.

## 2. 무엇이 바뀌고 무엇이 그대로인가

- **생김**: 표 `booth_live_check`(RLS 켬 · 정책 없음 · 표 권한 없음 · 외래 키 없음), 함수 `admin_confirm_booth_live(jsonb)` · `admin_booth_live_checks()`.

## 6. 문제가 생기면 — 함수만 즉시 끄기

1. SQL Editor 에 `supabase/rollback-booth-live-check.sql` 전체를 붙여넣고 Run(1초 안) → 맨 아래 4줄 모두 ‘맞음’.
2. 관리자 화면은 15~20초 안에(또는 [새로 고침]) [일괄 확인] 이 ‘준비 중’ 으로 돌아가고 ‘관리자 확인’ 표시가 사라집니다. ‘확인 필요’ 표시 · 수는 원래대로입니다.
3. **E** Run → 기존 함수 · 정책 · QR · PIN · 현황 지문이 3장 2번과 같음.
4. 기록 표 `booth_live_check` 는 남습니다(아무도 읽거나 쓰지 못함 — 감사 기록). 지우려면 CSV 로 내려받은 뒤 따로 승인.
5. 현황 데이터는 처음부터 바뀌지 않으므로 되돌릴 데이터가 없습니다. 다시 켜려면 적용 SQL 을 다시 Run(기록 이어 씀).

## 7. 시험 근거

- 실제 PostgreSQL 17(GitHub Actions 서비스 컨테이너, 독립 연결 6개 · 관리자 연결 statement_timeout 8s) **20/20** — 실행 40611129475(main 301cede 의 SQL). 이전 17/17 — 40499692269 · 40603690828.
  - 두 관리자 중복 0 · 운영자 값 유지 80/80 · 23:00 초기화와 겹쳐도 초기화 실패 0(처음 설계는 5/40 실패).
  - **결과 = 기록**: 모든 호출에서 confirmed 는 기록 정확히 1줄(확인 시각 · 확인한 값 시각까지 같음), skipped · failed 는 0줄, 결과에 없는 기록 0(L1b · L3a · L3b · L4 · L5c · L9 · L10).
  - **뒤섞기 80번**(L9: 관리자 셋 · 운영자 둘 · 초기화 27번 · 낡은 미리보기 20%) — 결과 6,183줄 중 요청 전체 실패 0 · 뜻밖의 결과 0 · 운영자 입력 실패 0 · 초기화 실패 0.
  - **뜻밖의 오류**(L10: 한 부스 기록에서 오류를 일부러 냄 + 운영자가 잡은 부스) — 요청은 정상 응답, 그 부스만 failed · failed:busy, 나머지 confirmed.
  - **3초 시간 초과**(L3b) — 다른 관리자가 3초 넘게 잡고 있으면 약 3초 뒤 전체 failed:busy 로 정상 응답 · 기록 0.
  - **부스 삭제**(L11) — 확인 기록은 남음 · 지운 부스는 skipped:not_found · 확인 중 삭제는 기다렸다가 성공.
- 복제 DB(지금 Production 단계 · main 301cede) 59/59 · PIN 상태 33/33 · 관리자 화면 72/72 · 기존 화면 점검 523/523 · 배포된 화면(함수 없음) 523/523.
- 점검 SQL D · E · F 는 복제 DB 에서 적용 앞뒤로 돌려 ‘기존 함수 지문 같음 · 확인 표 모두 맞음 · 수 일치’ 를 확인했습니다.
- 시험 코드: 브랜치 `claude/batch-confirm-tests`(`scripts/booth-data/BATCH-CONFIRM-TESTS.md`).
