# ‘확인 필요’ 일괄 확인 — Production 적용 · 현장 검증 절차

`supabase/migration-booth-live-check.sql` 을 Production 에 적용하는 절차입니다. **실행 직전에 최종 승인을 받고, SQL Editor 에서 운영 담당자가 직접 실행합니다.**
설계는 [ops-batch-confirm-and-notify.md](ops-batch-confirm-and-notify.md) 2장, 읽기 전용 점검 SQL 은 `supabase/check-booth-live-check.sql`(A~F · R · X · G 묶음).

## 0. 한 장 요약 — 운영 담당자용

모두 Supabase **SQL Editor** 에서 합니다. 파일은 `supabase/` 폴더의 세 개입니다: 점검 `check-booth-live-check.sql`(읽기만) · 적용 `migration-booth-live-check.sql` · 되돌리기 `rollback-booth-live-check.sql`.
점검 파일은 A~F · R · X · G 묶음으로 나뉘어 있으니 **그 묶음만 골라** Run 합니다. B · C · F · G 는 새 표가 있어야 하므로 적용 뒤에만 돕니다.

**언제**: 낮 10:00~17:00. 22:30~23:30(23:00 자동 초기화)과 행사 시간(11-06 · 07)은 피합니다. 당일 시간표는 3장.

**적용 보류**(하나라도 해당하면 적용하지 않음)

- **R**: 전날 23:00 초기화가 succeeded 가 아니거나 ‘실제 부스 어제 값 남음’ 이 0 이 아님.
- 운영팀이 모르는 관리자 입력(출처 admin)이 있고, 실행자를 확인하지 못했거나 아무도 하지 않았다고 확인됨 — 9장.

**적용(5분)** — 기준값은 **적용 직전에 새로** 받습니다(1장 표 등 예전 값은 쓰지 않음).

1. 점검 **A** Run → ‘선행 조건 있음’ · ‘새 이름 아직 없음’ 두 칸 모두 `true`. 아니면 멈춤.
2. 점검 **E** Run → 결과를 캡처(‘전’). ‘대기 기록 줄 / 마지막 id’ 의 **마지막 id** 를 적어 둠.
3. **최종 승인을 받은 뒤** 적용 파일 전체를 붙여넣고 Run → 오류 없음 · 맨 아래 10줄의 ‘맞음’ 이 모두 `true`.
   오류가 나면 멈춤(한 트랜잭션이라 아무것도 생기지 않음 — **A** 를 다시 돌려 ‘새 이름 아직 없음’ true 면 되돌리기 불필요).
4. 곧바로 점검 **E** 다시 Run → ‘전’ 캡처와 칸마다 같음. booth_live 두 칸만 다르면 **X** 로 그 사이 입력의 시각 · 출처를 대조(3장).
5. 관리자 화면 [새로 고침] → 부스 운영 현황의 [일괄 확인] 이 ‘준비 중’ 이 아니고 누를 수 있음.

**확인(적용 뒤 처음 쓰는 날)** — 5장 표를 그대로 따릅니다. 요점만:

- 일괄 확인은 **기록만 남깁니다**. 운영자 대기시간 · 마지막 입력 시각 · 관람객 화면은 바뀌지 않아야 합니다(**B** 앞뒤 · **G**).
- 확인한 부스는 ‘확인 필요’(30분 넘음) 표시가 **그대로 있고** 옆에 ‘관리자 확인 HH:MM’ 이 따로 붙습니다. 운영자가 새로 입력하면 그 표시가 사라집니다.
- 관리 조치의 수: 확인 필요 = 관리자 확인 + 아직 미확인.

**즉시 사용 중단 · 되돌리기 · 원인 확인 — 아래 중 하나라도 보이면 바로**

- 적용 3번에서 10줄 중 false · 4번에서 ‘전’ 과 다름(**X** 로 설명되는 booth_live 두 칸은 제외) · **X** 의 ‘기록과 안 맞는 현황’ 이 0 아님
- 관리자 확인만 했는데 **B** 의 지문 · 마지막 입력 · 대기 기록이 바뀜, **G** 의 ‘현황 그대로’ false 인데 ‘확인한 값 뒤 입력 수’ 0, 관람객 대기시간이 바뀜
- 운영자 입력이 실패한다는 신고 · 5장 기준과 다른 숫자 · 그 밖에 운영 상태나 입력 시각이 예상과 다르게 바뀜

1. 되돌리기 파일 전체를 붙여넣고 Run → 맨 아래 4줄의 ‘맞음’ 이 모두 `true`.
2. 관리자 화면 [새로 고침] → [일괄 확인] 이 다시 ‘준비 중’, ‘관리자 확인’ 표시 없음(‘확인 필요’ 는 원래대로).
3. 점검 **E** Run → ‘전’ 캡처와 같음(booth_live 두 칸은 **X** 로 대조).

되돌려도 운영 데이터는 그대로입니다(일괄 확인은 처음부터 booth_live 를 쓰지 않음). 기록 표 `booth_live_check` 는 지우지 말고 둡니다(감사 기록 · 아무도 읽거나 쓰지 못함).
**하지 않는 것**: 리허설 관리의 ‘채우기’(84곳 모두 씀), 부스 · QR · PIN 변경 · 개별 PIN 재발급, 기록 표 삭제, 원인 모를 입력값을 지우거나 고치기.

| 6 | 새 입력이 이김 | 그 부스 하나에서 운영자가 새로 입력 → **G** | 그 부스만 ‘현황 그대로’ false · ‘확인한 값 뒤 입력 수’ 1 · 출처 set(또는 touch) · 시각 = 방금. 관리자 두 화면 모두 그 부스가 확인 필요 · 관리자 확인에서 빠짐(15~20초 안) · C 의 기록은 남음 |

**즉시 사용 중단**: 관리자 확인만 했는데(1번 뒤, 6번 전) B 의 지문 · 마지막 입력 · 대기 기록이 바뀜, G 의 ‘현황 그대로’ false 인데 ‘확인한 값 뒤 입력 수’ 0,
관람객 대기시간이 바뀜, 운영자 입력 실패 신고 — 바로 [일괄 확인] 사용을 멈추고 6장 되돌리기 후 원인을 봅니다. 그 밖에도 하나라도 기준과 다르면 같습니다.

## 9. 원인 모를 관리자 입력이 있을 때 — 적용 보류 규칙

적용 전 **X** · 대기 기록에서 운영팀이 모르는 관리자 입력(출처 `admin`, 특히 여러 부스에 한꺼번에)이 보이면:

1. 운영팀이 **의도한 리허설 입력**이라고 확인 → 정상 진행.
2. 실행자를 **확인하지 못했거나**, 관리자 누구도 하지 않았다고 확인 → **Production SQL 적용 보류**. 아래 자료를 읽기 전용으로 점검해 보고합니다.
3. 어느 경우에도 그 값을 지우거나 고치지 않습니다(리허설 값은 23:00 자동 초기화가 지움).
